# Break-Glass Runbook

This runbook is for catastrophic situations that bypass the normal flow. Each procedure is intentionally manual, audited, and reversible only by a re-run.

The decisions log entries that justify these break-glass paths are dated 2026-05-06 (resolutions E and L in the inconsistency-resolution ADR).

## When to use this runbook

- You're an authorized developer with Supabase service-role access.
- Normal in-app paths cannot resolve the situation.
- The architect has approved the action in chat, ideally with a paper-trail (commit message, message thread) that the audit_log entry will reference.

## 1 — HO super-user has lost their password

**Symptom:** the single HO super-user (per architect override; only one HO super-user exists at deployment) cannot log in. There is no other HO user to issue a reset.

**Procedure:**

1. Generate a new bcrypt hash locally. From `supabase/seed/`:
   ```bash
   node -e "require('bcryptjs').hash(process.argv[1], 12).then(console.log)" 'NewSecurePassword!'
   ```
   Capture the resulting `$2a$12$...` string — that's the new hash.

2. In the Supabase dashboard SQL Editor (or via psql with the service-role connection string), run a single transaction:

   ```sql
   BEGIN;

   -- Reset the password
   UPDATE personnel
     SET password_hash = '$2a$12$<paste-new-hash-here>'
   WHERE role = 'ho'
     AND is_super_user = true
     AND email = 'neha.sharma@abfrl.com'  -- adjust if different
     AND active_to IS NULL;

   -- Audit the override
   INSERT INTO audit_log (
     actor_id, actor_type, action, entity_type, entity_id,
     before, after, context, occurred_at
   )
   SELECT
     id,                                 -- the affected user is the entity
     'system',                           -- actor_type for break-glass
     'ho_password_break_glass_reset',
     'personnel',
     id,
     '{"password_hash":"<redacted-old>"}'::jsonb,
     '{"password_hash":"<redacted-new>"}'::jsonb,
     jsonb_build_object(
       'reason', 'super-user lost password — break-glass per docs/playbooks/break-glass.md §1',
       'developer', 'YOUR_NAME',
       'approved_by_architect_at', '2026-05-06T00:00:00Z'  -- adjust to the actual approval time
     ),
     now()
   FROM personnel
   WHERE role = 'ho'
     AND is_super_user = true
     AND email = 'neha.sharma@abfrl.com';

   COMMIT;
   ```

3. Communicate the new password to the architect through an internal channel (Teams, in person). Never email.

4. Architect logs in, immediately changes the password from Settings.

5. Confirm the audit_log row is present and the override is recorded.

## 2 — Database is over Supabase free-tier ceiling

**Symptom:** Supabase emails or dashboard warns that the project is approaching/exceeding the 500 MB free-tier database limit. Per architect override 2026-05-06 (resolution K), Pro tier is off the table.

**Procedure:**

1. Check what's growing. From the SQL Editor:
   ```sql
   SELECT relname AS table,
          pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
   FROM pg_class c
   JOIN pg_namespace n ON n.oid = c.relnamespace
   WHERE n.nspname = 'public' AND c.relkind = 'r'
   ORDER BY pg_total_relation_size(c.oid) DESC
   LIMIT 20;
   ```

2. If `audit_log` is the largest table, run the Phase 2 archival job (when implemented). Until that job exists, the manual fallback is:

   ```sql
   -- Run during low-activity hours. Trims audit_log to last 90 days.
   -- WARNING: archived rows are deleted without backup at this point.
   -- Once the archival job lands, route trimmed rows to Supabase Storage first.
   DELETE FROM audit_log
   WHERE occurred_at < (now() - INTERVAL '90 days');
   ```

3. If `submissions` is the largest table, the right answer is *not* to delete. Synthetic submissions can be regenerated by re-running the seed; production submissions cannot. Talk to the architect first.

4. For evidence files in Supabase Storage (separate from the database limit), audit periodically:
   - Old approved submissions' photos can be moved to a colder Storage bucket if Supabase ever splits hot/cold — for now, leave them.

## 3 — The seed re-run is blocked by audit_log

**Symptom:** running `npm run seed:wave1` fails with a foreign-key error citing `audit_log` blocking deletion of `personnel`.

**Procedure:**

1. The audit_log holds rows that reference the personnel about to be deleted. Migration 002 made `audit_log.actor_id ON DELETE SET NULL` so this should be rare; if it still happens, it's because a non-actor reference exists somewhere (e.g., `entity_id` pointing at a personnel row).

2. In the SQL Editor:
   ```sql
   TRUNCATE audit_log CASCADE;
   ```

3. Re-run the seed.

4. Audit_log is rebuilt by the seed's submission-insert path. Production audit_log cannot be truncated this way — the seed only runs against the demo project.

## 4 — A migration must be reverted

**Reminder:** migrations are forward-only by project policy. There is no clean rollback.

**Procedure:**

1. Open a new migration `004_reverts_NNN.sql` (or whatever number is next) that *constructs the desired prior state* — re-adds dropped columns with their original constraints, or re-creates dropped tables from a backup.

2. Apply it. Update `decisions.md` with an entry explaining the revert and what the new direction is.

3. Never edit a previously-applied migration file. Even if you discover it was wrong: a new migration that fixes it is the only path.
